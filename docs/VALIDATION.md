# Проверка системы

Что проверяется: корректность связки **D435i → `SensorData` → RTAB-Map** и поведение системы
в реальных условиях. Математика самого RTAB-Map не проверяется — она берётся как данность,
как и всё остальное в этом проекте (см. [README](../README.md)).

Проверка состоит из двух частей: прогоны с камерой в руках и разбор того, что осталось после
прогона. Разбор автоматизирован скриптом `scripts/validate_run.py`, всё остальное смотрится
глазами в HUD, консоли и `rtabmap-databaseViewer`.

## Скрипт

```bash
./scripts/validate_run.py rtabmap_minimal.db                                   # база
./scripts/validate_run.py --traj rtabmap_minimal_trajectory.txt rtabmap_minimal.db
./scripts/validate_run.py runs/*.db                                            # сравнение прогонов
```

База открывается только на чтение, ничего не пересчитывается: все числа уже лежат в `.db`.
Оптимизированные позы берутся из файла траектории, если он передан, иначе — из последней
оптимизации, сохранённой в базе. Код возврата 1, если есть хотя бы один FAIL.

Одиннадцать проверок:

| Проверка | Что означает FAIL |
|---|---|
| `export` | в траекторию попали не все узлы или время не растёт |
| `map segments` | сегмент карты (после сброса одометрии) потерялся при экспорте |
| `gravity links` | gravity-рёбер нет при включённом IMU или они есть не у всех узлов (WARN) |
| `IMU agreement` | среднее расхождение roll/pitch с оптимизированными позами > 2° — ошибка осей в `imuLocalTransform` |
| `IMU latency` | ошибка растёт вместе со скоростью вращения — ориентация IMU отстаёт от кадра (WARN) |
| `loop closures` | принято замыкание с числом inliers ниже `Vis/MinInliers` |
| `closure plausibility` | замыкание связывает позы дальше 2 м или на 60° — при диапазоне глубины 4 м это подозрительно (WARN) |
| `drift` | сравнение одометрии с оптимизированным графом, WARN при дрейфе > 5 % пути |
| `covariances` | в графе есть рёбра с нулевой или нечисловой информационной матрицей |
| `timing` | RTAB-Map не успевает за `Rtabmap/DetectionRate` (WARN) |
| `calibration` | калибровка менялась в течение прогона |

Пороги — константы в шапке скрипта, они подобраны по первым прогонам и рассчитаны на уточнение.

## Прогоны с камерой

Каждый прогон — в отдельную базу, иначе она перезаписывается:

```bash
mkdir -p runs
./scripts/run.sh --db runs/t6_1.db --cloud runs/t6_1.pcd
cp rtabmap_minimal_trajectory.txt runs/t6_1.txt     # имя файла траектории не настраивается
```

Точность везде приблизительная: старт отмечается скотчем на полу, углы сверяются
с инклинометром в телефоне. Идеально проходить маршрут не требуется.

| Тест | Как делать | Ожидаемый результат |
|---|---|---|
| **T0 Статика** | Камера неподвижно на столе, текстурная сцена, 60 с | Нет предупреждения про global time; в HUD нет LOST; узлов 2–3; дрейф одометрии < 2 см |
| **T1 Масштаб** | Пройти вдоль рулетки 3 м и обратно | `drift`: длина пути ≈ 6 м ±5 % |
| **T2 Alignment** | Коробка на столе в 1–2 м, медленный обход на 90° | В `rtabmap-databaseViewer` границы глубины совпадают с краями объекта, без сдвига в одну сторону |
| **T3 Оси IMU** | По 10 с: ровно на столе → наклон вперёд ~30° → на боку ~90° | `IMU agreement` PASS; наклон совпадает с инклинометром по величине и знаку ±3° |
| **T4 Задержка IMU** | Повороты ±45° сначала медленно (~20°/с), потом быстро (~150°/с), по 30 с | `IMU latency` PASS. WARN означает, что ориентация IMU берётся не на момент кадра |
| **T5 Потеря трекинга** | Маршрут ~10 м, в середине закрыть объектив на 3 с, затем вернуться в снятую зону | В HUD LOST и восстановление; `map segments` WARN (это норма), но **не** FAIL; после возврата появляется замыкание |
| **T6 Петля** | Петля 15–30 м с возвратом на метку старта (±20 см), 2 круга | На втором круге есть замыкания; `drift`: старт→финиш заметно меньше, чем по одометрии; `closure plausibility` PASS |
| **T7 Повторяемость** | T6 пять раз одним маршрутом при том же освещении | `./scripts/validate_run.py runs/t6_*.db`: разброс длины пути < 5 %, все прогоны замыкают петлю |
| **T8 Влияние IMU** | Три прогона T6 с IMU против трёх с `--no-imu` | С IMU: `IMU agreement` PASS, ошибка замыкания не хуже, меньше наклон карты |

Порядок: T0 → T3 → T1 → T6 → T5 → T4 → T7 → T8. Первые четыре занимают около 20 минут
и ловят грубые ошибки интеграции.

Влияние IMU можно оценить и без второй съёмки — переобработав те же данные без gravity:

```bash
source /opt/ros/humble/setup.bash        # иначе утилиты не найдут librtabmap_*.so
rtabmap-reprocess --Optimizer/GravitySigma 0 runs/t6_1.db runs/t6_1_noimu.db
./scripts/validate_run.py runs/t6_1.db runs/t6_1_noimu.db
```

Две особенности такого сравнения. Gravity-рёбра в выходной базе остаются — это измерения,
а не ограничения, обнуляется только их вес при оптимизации, поэтому разница видна
в `IMU agreement`, а не в числе рёбер. На проверочном прогоне p95 выросло с 2,5°/3,7°
до 5,7°/6,6° — это и есть вклад gravity. И переобработка заводит новую сессию, поэтому
`map segments` покажет на один сегмент больше, чем было в исходной базе.

## Что скриптом не проверяется

Покадровые данные нигде не сохраняются: время цветного и depth-кадра, пропуски кадров,
частота IMU, число и длительность потерь трекинга, features/inliers одометрии. В базе
RTAB-Map их нет — статистика пишется только по узлам карты. Поэтому в T0, T4 и T5 это
смотрится вживую в HUD (`TRACKING` / `LOST`, features, inliers, Гц) и в строке состояния
консоли, которая печатается раз в две секунды.
